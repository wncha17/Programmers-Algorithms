## 📝 [Hash] 완주하지 못한 선수 (Lv. 1)
> **문제 링크:** [https://school.programmers.co.kr/learn/courses/30/lessons/42576]

### 1. 🔍 Key Signal (문제의 단서)
- **키워드:** "단 한 명의 선수를 제외하고는 모든 선수가 완주", "이름이 담긴 배열", "중복 가능성(동명이인)"
- **알고리즘:** 해시(Hash)
- **판단 근거:**
  1. 참가자(participant)와 완주자(completion)의 길이는 최대 100,000이다.
  2. 이중 루프(O(N^2))로 비교하면 100억 번의 연산이 필요해 시간 초과가 발생한다.
  3. 이름(문자열)을 키(Key)로 삼아 빠르게(O(1)) 데이터를 찾고 개수를 세어야 하므로 해시가 최적이다.

### 2. 💡 Strategy (설계)
1. 빈 해시 테이블(딕셔너리)을 생성한다.
2. participant를 순회하며 {이름: 인원수} 형태로 저장한다. (동명이인은 +1)
3. completion을 순회하며 해시 테이블에서 해당 이름의 인원수를 -1씩 뺀다.
4. 마지막에 인원수가 0이 아닌(1인) 이름을 찾아서 반환한다.

### 3. ⚠️ Edge Case & Pitfalls
- **동명이인**: 단순히 set을 써서 차집합을 구하면 동명이인 처리가 안 된다. (예: 'mislav'가 2명인데 1명만 완주한 경우)
- **효율성**: Python의 dict는 내부적으로 해시 테이블로 구현되어 있어 매우 빠르다. 더 세련된 풀이를 원한다면 collections.Counter 활용 가능.

### 4. 🛠️ Implementation (코드 요약)
- **[Solution 1]: Hash Dictionary 활용 (정석적 접근)**
  - 로직: 딕셔너리에 참가자 수를 카운트하고, 완주자를 뺄셈하여 남는 자를 찾음.
  - 특징: 가장 범용적이며, 해시의 원리(O(1) 탐색)를 가장 잘 보여줌.

- **[Solution 2]: Python collections.Counter 활용 (언어 특화)**
  - 로직: 객체 간의 뺄셈 연산 기능을 활용하여 한 줄로 해결.
  - 특징: 가독성이 뛰어나고 구현 속도가 빠름. 실무 생산성 강조 시 유리.

- **[Solution 3]: Sorting 활용 (메모리 효율적 접근)**
  - 로직: 두 배열을 정렬한 뒤, 인덱스 별로 비교하다가 값이 다른 지점의 참가자가 정답.
  - 특징: 해시 테이블을 위한 추가 메모리 할당이 적음. 해시 충돌 위험이 없는 환경에서 고려할 만함.

### 5. 🏟️ Real-world Connection
- **데이터 정합성 검증**: 대규모 결제 트랜잭션이나 차량 데이터 수신 리스트 대조 시, 누락된 데이터(Missing Data)를 O(N)의 속도로 빠르게 식별하여 시스템 신뢰성을 보장함.

## 📝 [Hash] 폰켓몬 (Lv. 1)
> **문제 링크:** [https://school.programmers.co.kr/learn/courses/30/lessons/1845]

### 1. 🔍 Key Signal (문제의 단서)
- **키워드:** "N/2마리 선택", "가장 많은 종류의 폰켓몬", "중복된 번호는 같은 종류"
- **알고리즘:** Hash (Set)
- **판단 근거:**
  1. 선택할 수 있는 최대 마리수는 정해져 있다.
  2. 우리가 관심 있는 건 '마리수'가 아니라 '종류의 수'이다.
  3. 종류를 파악하기 위해 중복을 제거하는 가장 빠른 방법은 해시 기반의 set 자료구조를 사용하는 것이다.

### 2. 💡 Strategy (설계)
- **[Solution 1] set을 활용한 중복 제거 (가장 직관적)**
  - 로직: 폰켓몬 리스트를 set으로 변환하여 고유한 종류의 수를 구하고, 이를 N/2와 비교함.
  - 특징: 코드 한 줄로 해결 가능하며, 해시 셋의 시간 복잡도(O(N))를 활용함.

- **[Solution 2] dict를 활용한 카운팅 (확장성 고려)**
  - 로직: 딕셔너리에 각 폰켓몬의 종류별 마리수를 저장한 뒤, 딕셔너리 키의 개수를 확인함.
  - 특징: 만약 문제에서 "특정 종류의 폰켓몬을 몇 마리 가졌는지도 출력하라"는 요구사항이 추가될 경우 대응하기 좋음.

### 3. ⚠️ Edge Case & Pitfalls
- **과도한 최적화의 함정**: N/2보다 종류가 많을 때, 어떤 폰켓몬을 골라야 하는지 고민할 필요가 없다. "최대 종류의 수"만 물었으므로 단순 비교(min)로 끝내야 한다.

## 📝 [Hash] 전화번호 목록 (Lv. 2)
> **문제 링크:** [https://school.programmers.co.kr/learn/courses/30/lessons/42577]

### 1. 🔍 Key Signal (문제의 단서)
- **키워드:** "한 번호가 다른 번호의 접두어인 경우", "번호의 길이는 최대 20", "전체 번호 개수는 최대 1,000,000"
- **알고리즘:** Hash (Dictionary/Set) or Sorting
- **판단 근거:**
  1. 데이터가 100만 개이므로 O(N^2)의 이중 루프 비교는 절대 불가능하다.
  2. 각 번호를 잘라가며(Substring) 해시 맵에 존재하는지 확인하는 O(N * L) (L: 전화번호 길이) 방식이 필요하다.

### 2. 💡 Strategy (설계)
- **[Solution 1] Hash를 활용한 접두어 찾기 (백엔드 설계형)**
  - 로직: 모든 전화번호를 해시 맵(dict)에 먼저 등록. 그 후, 각 번호를 한 글자씩 늘려가며 자른 값이 해시 맵에 있는지 확인함.
  - 문자열 길이가 짧을 때(최대 20) 매우 강력하며, 해시의 평균 탐색 시간 O(1)을 극대화함.

- **[Solution 2] Sorting을 활용한 인접 비교 (수학적 직관)**
  - 로직: 전화번호를 정렬하면 비슷한 번호(접두어가 같은 번호)끼리 이웃하게 됨. 바로 뒷 번호와만 비교.
  - 특징: 추가 메모리 사용이 거의 없으며 구현이 매우 간결함.

### 3. ⚠️ Edge Case & Pitfalls
- **startswith 오용**: 이중 루프 안에서 startswith를 쓰면 결국 O(N^2)이 되어 효율성 테스트에서 탈락한다. 정렬을 통해 '인접 비교'로 차수를 낮추는 것이 핵심이다.

### 4. 🛠️ Implementation (코드 요약)
- (생략)

### 5. 🏟️ Real-world Connection
- **API Gateway 라우팅 패턴 매칭**: 현대자동차의 수많은 마이크로서비스(MSA) 환경에서 요청된 URL(예: /api/v1/car/status)이 허용된 서비스 접두어(prefix)에 해당하는지 빠르게 판단하여 트래픽을 분산할 때 이 로직이 쓰인다. 해시 기반의 접두어 체크는 대규모 트래픽 환경에서 응답 속도를 결정짓는 핵심 요소이다.

## 📝 [Hash] 의상 (Lv. 2)
> **문제 링크:** [https://school.programmers.co.kr/learn/courses/30/lessons/42578]

### 1. 🔍 Key Signal (문제의 단서)
- **키워드:** "서로 다른 옷의 조합", "각 종류별로 최대 1가지", "최소 한 개의 의상은 입음"
- **알고리즘:** Hash(Dictionary) + 조합론(Combinations)
- **판단 근거:**
  1. 의상의 이름이 아닌 '종류(Category)'를 기준으로 데이터를 묶어야 한다.
  2. 종류별 개수만 알면 전체 조합의 수를 수학적으로 계산할 수 있으므로, 카테고리를 Key로 하는 해시맵이 최적이다.

### 2. 💡 Strategy (설계)
- **[Solution] Hash Map을 활용한 경우의 수 계산**
  - 로직: 종류별 의상 개수를 구한 뒤, 각 종류마다 '입지 않는 경우'를 포함하여 계산함.
  - 공식: (A+1) * (B+1) * (C+1) ... -1

### 3. ⚠️ Edge Case & Pitfalls
- **조합 함수(itertools.combinations) 사용 금지**: 모든 조합을 실제로 생성하면 2^N의 시간이 걸려 절대 통과할 수 없다.
- **자료구조의 목적**: 이 문제에서 의상의 '이름'은 함정, 오직 '종류'의 개수만 카운트.

## 📝 [Hash] 베스트 앨범 (Lv. 3)
> **문제 링크:** [https://school.programmers.co.kr/learn/courses/30/lessons/42579]

### 1. 🔍 Key Signal (문제의 단서)
- **키워드:** "장르별 가장 많이 재생된", "장르 내에서 많이 재생된", "재생 횟수 같으면 고유 번호 낮은 순", "최대 2개씩"
- **알고리즘:** Hash(Double Dictionary) + 다중 조건 Sorting
- **판단 근거:**
  1. 장르별 총합을 구해야 하므로 {장르: 총합} 해시가 필요하다.
  2. 장르 내 개별 곡 정보(인덱스, 재생수)도 관리해야 하므로 {장르: [(재생수, 인덱스), ...]} 형태의 중첩 해시가 필요하다.
  3. 여러 기준(장르 합계 -> 곡별 재생수 -> 인덱스)에 따른 정렬이 핵심이다.

### 2. 💡 Strategy (설계)
- **[Solution] 중첩 해시와 정렬의 조합**
  1. 데이터 수집: genre_total{장르: 총합}과 genre_songs{장르: [(재생수, 인덱스)]}를 만듦.
  2. 장르 정렬: genre_total을 기준으로 내림차순 정렬하여 어떤 장르부터 수록할지 결정함.
  3. 곡 정렬 및 추출: 각 장르 내의 곡들을 재생수(내림차순), 인덱스(오름차순) 순으로 정렬하고 상위 2개를 뽑음.

### 3. ⚠️ Edge Case & Pitfalls
- **다중 정렬 기준**: lambda 함수에서 -x[0]처럼 마이너스 부호를 붙여 내림차순과 오름차순을 한 번에 처리하는 테크닉이 중요하다.
- **장르 당 곡 개수**: 장르에 곡이 하나만 있는 경우를 대비해 min(len(songs), 2)와 같은 처리가 필요하지만, 파이썬 슬라이싱([:2])은 개수가 적어도 에러 없이 작동하므로 이를 활용하면 간결하다.

### 4. 🛠️ Implementation (코드 요약)
- (생략)

### 5. 🏟️ Real-world Connection
- **차량용 콘텐츠 추천 엔진**: 현대자동차의 인포테인먼트 시스템에서 사용자에게 '가장 많이 들은 장르 Top 2'를 보여주거나, '최근 가장 많이 팔린 차종별 베스트 옵션 조합'을 랭킹으로 산출할 때 사용됩니다. 대량의 원시 로그(Plays)를 해시로 요약(Aggregating)하고 정렬하여 의미 있는 정보로 변환하는 백엔드 API의 핵심 구조입니다.
