## 📝 [Stack/Queue] 같은 숫자는 싫어 (Lv. 1)
> **문제 링크:** [https://school.programmers.co.kr/learn/courses/30/lessons/12906]

### 1. 🔍 Key Signal (문제의 단서)
- **키워드:** "연속적으로 나타나는 숫자는 제거", "제거 후 남은 수들을 반환할 때는 원소들의 순서를 유지"
- **알고리즘:** 스택(Stack)
- **판단 근거:**
  1. 들어온 순서대로 처리해야 하므로 선형 자료구조가 필요하다.
  2. 새로운 원소를 넣기 전에 '직전에 들어간 원소'와 비교해야 한다.
  3. '가장 최근 데이터'와 비교하는 특성은 전형적인 스택의 LIFO(Last In First Out) 구조를 활용하면 매우 효율적이다.

### 2. 💡 Strategy (설계)
- **[Solution 1]: 스택(Stack)을 활용한 정석 풀이**
  - 로직: 빈 리스트(스택)를 만들고, 원본 배열을 순회하며 스택의 top 원소와 현재 원소가 다를 때만 push.
  - 특징: 가장 직관적이며, O(N)의 시간 복잡도로 해결 가능함.

- **[Solution 2]: 파이썬 슬라이싱을 활용한 최적화**
  - 로직: 결과 리스트에 첫 원소를 미리 넣고, 다음 원소부터 바로 앞 원소와 비교.
  - 특징: 스택을 명시적으로 쓰지 않아도 개념적으로는 동일하며, 코드가 매우 간결함.

### 3. ⚠️ Pitfalls
- **set 사용 금지**: 이 문제는 '중복 제거'가 아니라 '연속된 중복 제거'이다. set을 쓰면 순서가 뒤섞이고, 연속되지 않은 중복(예: [1,2,1])까지 사라져서 오답이 된다.
- **인덱스 에러**: arr[i-1]과 비교할 때 첫 번째 원소(i=0) 처리를 빠뜨리면 IndexError가 날 수 있으니 주의해야 한다.

### 4. 🏟️ Real-world Connection
- **이벤트 스트리밍 데이터 중복 필터링**: 현대자동차 커넥티드 카에서 서버로 0.1초마다 상태 정보를 보낼 때, 차량이 멈춰있으면 똑같은 좌표 데이터가 수천 번 들어올 수 있습니다.  
  이때 백엔드 서버는 직전 데이터와 비교하여 변화가 있을 때만 DB에 기록함으로써 저장 공간과 네트워크 비용을 획기적으로 줄인다.

## 📝 [Stack/Queue] 기능개발 (Lv. 2)
> **문제 링크:** [https://school.programmers.co.kr/learn/courses/30/lessons/42586]

### 1. 🔍 Key Signal (문제의 단서)
- **키워드:** "뒤에 있는 기능이 앞에 있는 기능보다 먼저 완료될 수 있지만, 앞의 기능이 배포될 때 함께 배포", "배포 순서 고정"
- **알고리즘:** 큐(Queue)
- **판단 근거:**
  1. 작업 순서가 정해져 있고, 먼저 들어온 작업이 먼저 나가야 하는 FIFO(First-In, First-Out) 구조이다.
  2. 앞 작업의 완료 시점이 뒤 작업의 배포 시점에 직접적인 영향을 주는 '의존성'이 핵심이다.

### 2. 💡 Strategy (설계)
- **[Solution 1] 남은 일수를 계산하여 큐로 처리 (정석적 접근)**
  - 로직: 각 작업이 끝나기까지 남은 일수를 먼저 계산하여 큐에 담음. 큐의 첫 번째 값(기준점)보다 작거나 같은 값들은 한 번에 배포(pop).
  - 특징: 문제의 요구사항을 단계별로 가장 충실히 구현한 방식.

- **[Solution 2] 큐 없이 '배포 가능일' 변수 하나로 처리 (공간 최적화)**
  - 로직: 큐를 명시적으로 쓰지 않고, 현재까지의 '최대 소요 일수'를 갱신하며 결과 리스트의 마지막 값을 수정함.
  - 특징: 추가 리스트(days) 생성을 최소화하여 메모리 효율을 높인 백엔드 최적화 스타일.

### 3. ⚠️ Pitfalls
- **올림 처리(Ceil)**: (100 - progress) / speed 계산 시 나머지가 있다면 반드시 하루가 더 필요하다. 이를 math.ceil 또는 (99 - p) // s + 1과 같이 정확히 처리해야 한다.

### 4. 🏟️ Real-world Connection
- **차량 소프트웨어 배포 관리 (OTA Updates)**: 현대자동차 ICT본부에서 차량의 인포테인먼트, 제어기 등 여러 모듈의 업데이트 패키지를 배포할 때 사용된다.  
  각 모듈의 업데이트 설치 속도(speeds)는 다르지만, 보안이나 시스템 안정성을 위해 반드시 특정 순서대로 설치가 완료되어야 하는 경우,  
  앞선 패키지 설치가 끝날 때까지 대기했다가 함께 승인 처리를 내리는 스케줄링 로직의 모태가 된다.

## 📝 [Stack/Queue] 올바른 괄호 (Lv. 2)
> **문제 링크:** [https://school.programmers.co.kr/learn/courses/30/lessons/12909]

### 1. 🔍 Key Signal (문제의 단서)
- **키워드:** "괄호가 바르게 짝지어졌는지", "'('로 열렸으면 반드시 ')'로 닫혀야 함"
- **알고리즘:** 스택(Stack)
- **판단 근거:**
  1. 괄호는 가장 나중에 열린 것이 가장 먼저 닫혀야 하는 LIFO(Last-In, First-Out) 구조이다.
  2. ')'가 나왔을 때, 가장 직전에 열린 '('가 있는지 확인하고 짝을 맞춰 제거해야 한다.

### 2. 💡 Strategy (설계)
- **[Solution 1] 스택(Stack) 리스트 활용 (정석적 접근)**
  - 로직: 문자열을 순회하며 '('는 스택에 넣고, ')'는 스택에서 꺼냄(pop).
  - 특징: 스택의 동작 원리를 가장 명확하게 보여줌.
 
- **[Solution 2] 카운터(Counter) 변수 활용 (공간 최적화)**
  - 로직: 실제 스택 리스트를 만들지는 않고, 숫자를 더하고 빼는 방식(+1, -1)으로 스택의 길이를 모방함.
  - 특징: 공간 복잡도를 O(1)로 줄이는 백엔드 최적화 기법.

### 3. ⚠️ Pitfalls
- **중간 종료 조건**: 루프가 끝난 뒤에만 체크하는게 아니라, 중간에 balance가 음수가 되는 순간 바로 False 반환해야 함.  
- **빈 스택 팝**: Solution 1에서 if not stack 체크 없이 pop()을 하면 런타임 에러 발생.

## 📝 [Stack/Queue] 프로세스 (Lv. 2)
> **문제 링크:** [https://school.programmers.co.kr/learn/courses/30/lessons/42587]

### 1. 🔍 Key Signal (문제의 단서)
- **키워드:** "우선순위가 높은 프로세스가 있으면 다시 큐에 넣음", "실행 순서를 찾기", "location(내가 찾는 프로세스의 위치)"
- **알고리즘:** 큐(Queue) + 시뮬레이션
- **판단 근거:**
  1. 프로세스들이 줄을 서서 기다리는 구조이므로 큐를 사용한다.
  2. 단순히 먼저 온 순서가 아니라, 전체 큐를 확인하여 최댓값(우선순위)이 있는지 매번 체크해야 한다.
  3. 내가 타겟팅한 프로세스가 몇 번째로 나가는지 추적하는 '인덱스 관리'가 핵심이다.

### 2. 💡 Strategy (설계)
- **[Solution] deque를 활용한 프로세스 시뮬레이션**
  - 로직
    1. 각 프로세스의 (우선순위, 원래 인덱스)를 튜플로 묶어 큐에 넣기
    2. 큐에서 하나를 꺼냈을 때, 남은 큐 안에 더 높은 우선순위가 있는지 확인하기
    3. 더 높은 게 있다면 뒤로 다시 넣고, 없다면 실행(count += 1)하기
    4. 실행한 프로세스의 원래 인덱스가 location과 같다면 정답을 반환하기

### 3. ⚠️ Pitfalls
- **인덱스 유실**: 큐가 회전(뒤로 다시 넣기)할 때마다 프로세스의 위치가 바뀜. 따라서 처음에 enumerate로 고유번호(Index)를 박아두지 않으면,  
  내가 찾던 것이 어떤 것인지 잊어버리게 됨.
- **효율성**": any() 함수는 매번 큐를 순회하므로 O(N^2)의 시간이 걸릴 수 있음. 만약 데이터가 더 크다면 '최대 힙(Max Heap)'이나 '우선순위 큐'를  
  병행해서 최댓값을 O(1)로 찾는 최적화가 필요할 수 있음을 알아두기.

### 4. 🏟️ Real-world Connection
- **비상 호출(eCall) 및 긴급 메시지 처리**: 현대자동차 커넥티드 카 서버에는 수많은 요청(음악 재생, 경로 탐색 등)이 들어온다.  
 하지만 '에어백 전개'나 '긴급 SOS 서비스' 같은 높은 우선순위의 프로세스가 인입되면, 일반적인 요청들은 큐의 뒤로 밀리고 긴급 메시지가 즉시 처리되어야 한다.  
 이러한 우선순위 기반 작업 스케줄링(Priority Scheduling)의 기본 원리가 이 문제에 담겨 있다.

## 📝 [Stack/Queue] 다리를 지나는 트럭 (Lv. 2)
> **문제 링크:** [https://school.programmers.co.kr/learn/courses/30/lessons/42583]

### 1. 🔍 Key Signal (문제의 단서)
- **키워드:** "정해진 순서대로", "다리 길이(time)", "견딜 수 있는 무게(weight)", "모든 트럭이 건너는 최소 시간"
- **알고리즘:** 큐(Queue) 시뮬레이션
- **판단 근거:**
  1. 트럭들이 순서대로 다리에 진입하고 나가는 FIFO 구조이다.
  2. 다리 자체를 하나의 큐로 보고, 트럭이 한 칸씩 이동하는 것을 시간(초)의 경과로 치환해야 한다.

### 2. 💡 Strategy (설계)
- **[Solution] 다리 길이만큼의 빈 큐를 활용한 시뮬레이션**
  - 로직
    1. 다리 길이(bridge_length)만큼 0으로 채워진 큐를 만들기 (비어있는 다리 상태)
    2. 매 초마다 큐에서 하나를 빼고(popleft), 새로운 트럭이 들어올 수 있는지 체크하기
    3. (현재 다리 위 무게 + 다음 트럭 무게) <= weight 라면 트럭을 진입시키고, 아니라면 0을 넣어 시간을 보내기
    4. 대기 중인 트럭이 모두 다리에 올라갈 때까지 반복한 후, 마지막 트럭이 빠져나가는 시간을 더하기

### 3. ⚠️ Pitfalls
- **시간 복잡도 최적화**: 매 반복문마다 sum(bridge)를 호출하면 O(Time * Bridge_Length)가 되어 효율성에서 떨어질 수 있다.  
  current_weight 변수를 따로 두어 더하고 빼는 방식으로 관리하는 것이 백엔드 고성능 로직의 기본이다.
- **마지막 처리**: 반복문은 마지막 트럭이 다리에 '올라가는' 순간 종료된다. 그 트럭이 다리를 완전히 '건너는' 시간(bridge_length)을 마지막에 꼭 더해주어야 한다.

### 4. 🏟️ Real-world Connection
- **스마트 팩토리 컨베이어 벨트 제어**: 현대자동차 생산 라인에서 차체가 컨베이어 벨트를 따라 이동할 때,  
  벨트가 견딜 수 있는 최대 하중과 공정 구간별 소요 시간을 계산하여 차체 투입 간격을 조절하는 로직과 일치합니다.

- **네트워크 트래픽 쉐이핑(Traffic Shaping)**: 서버의 네트워크 대역폭(Weight)이 제한적일 때,  
  대기 중인 데이터 패킷(Trucks)을 일정 속도로 전송하며 지연 시간(Time)을 최소화하는 알고리즘의 기초가 됩니다.

## 📝 [Stack/Queue] 주식가격 (Lv. 2)
> **문제 링크:** [https://school.programmers.co.kr/learn/courses/30/lessons/42584]

### 1. 🔍 Key Signal (문제의 단서)
- **키워드:** "가격이 떨어지지 않은 기간", "초 단위로 기록된 주식가격"
- **알고리즘:** 스택(Stack)
- **판단 근거:**
  1. 모든 가격을 서로 비교하면 O(N^2)이 걸리지만, 스택을 쓰면 O(N)에 해결 가능하다.
  2. 현재 가격보다 '낮은 가격'이 나오기 전까지는 계속 스택에 쌓아두며 대기하는 구조이다.
  3. 가격이 떨어지는 '사건'이 발생했을 때만 스택에서 꺼내어 기간을 계산한다.

### 2. 💡 Strategy (설계)
- **[Solution] 인덱스를 저장하는 스택 활용**
  - 로직
    1. 가격 배열을 순회하며 '인덱스'를 스택에 넣기
    2. 만약 '현재 가격 < 스택 top의 가격'이라면? -> 가격이 떨어진 것!
    3. 스택에서 꺼내어 '현재 시간 - 기록된 시간'으로 버틴 기간을 계산하기
    4. 순회가 끝나고 스택에 남은 인덱스들은 '끝까지 가격이 떨어지지 않은'것들이므로 전체 시간과의 차이 계산하기

### 3. ⚠️ Pitfalls
- **마지막 1초**: 문제 조건에서 "1초 뒤에 가격이 떨어져도 1초간은 떨어지지 않은 것"으로 간주한다. 즉, 마지막 데이터의 결과값은 항상 0이 된다.

### 4. 🏟️ Real-world Connection
- **차량 이상 징후 탐지 시스템**: 전기차 배터리의 전압이나 모터의 온도가 일정 수준 이상으로 유지되는 기간을 모니터링할 때 사용된다.  
  정상 범위를 벗어나는(가격이 떨어지는) 시점이 오기 전까지의 '정상 지속 시간'을 실시간으로 계산하여 대시보드에 표출하거나 경고를 보내는 엔진의 기본 로직이다.
